# 给 Claude：CalmPaws 服务器配合修改说明

日期：2026-06-10

## 结论

APP 侧已经把历史曲线做了临时兜底：优先使用 Firebase Bearer token 调服务器，如果 `/api/history` 返回 401，再用旧的设备 key 读取历史数据。因此 GitHub Pages 预览里 24h / 7d / 30d 曲线目前可以显示。

但这只是兼容方案。正式联调需要服务器把 `/api/history/<device_id>` 的鉴权逻辑补齐到和 `/api/status/<device_id>`、`/api/alerts/<device_id>`、`/api/user/devices` 一致，否则 APP 的用户体系仍然没有闭环。

## P0：历史接口需要支持 Firebase Bearer 鉴权

### 现象

同一个已登录测试账号，同一个设备 `collar_001`：

- `GET /api/user/devices` + `Authorization: Bearer <Firebase ID token>`：200
- `GET /api/status/collar_001` + `Authorization: Bearer <Firebase ID token>`：200
- `GET /api/alerts/collar_001` + `Authorization: Bearer <Firebase ID token>`：200
- `GET /api/history/collar_001?range=24h` + `Authorization: Bearer <Firebase ID token>`：401
- `GET /api/history/collar_001?range=7d` + `Authorization: Bearer <Firebase ID token>`：401
- `GET /api/history/collar_001?range=30d` + `Authorization: Bearer <Firebase ID token>`：401
- `GET /api/history/collar_001?range=24h&key=<旧设备key>`：200
- `GET /api/history/collar_001?range=7d&key=<旧设备key>`：200
- `GET /api/history/collar_001?range=30d&key=<旧设备key>`：200

服务器日志也能看到同一时间段内，不带 query key 的 history 请求 401，带旧 key 的 history 请求 200。`OPTIONS /api/history/...` 是 200，并且允许 `Authorization` header，所以这不是 CORS 问题。

### 期望行为

`/api/history/<device_id>` 应该支持两种鉴权路径：

1. APP 用户路径：`Authorization: Bearer <Firebase ID token>`
   - 验证 token。
   - 从 token 取 `uid`。
   - 检查该 `uid` 是否绑定/拥有 `device_id`。
   - 绑定正确时返回历史数据。
   - token 无效返回 401。
   - token 有效但设备不属于该用户返回 403。

2. 设备/兼容路径：`?key=<旧设备key>`
   - 可保留给 ESP32、调试脚本、后台兼容使用。
   - 但正式 APP 不应该依赖这个 key。

### 为什么必须改

现在 APP 已经进入 Firebase 用户体系。如果历史接口只认旧 key，就会出现：

- 登录用户能看到实时状态，但历史曲线必须靠 APP 内置兼容 key 才能显示。
- 设备绑定关系无法真正保护历史数据。
- 后续多用户、多设备、解绑、转移设备都会有权限漏洞或数据串号风险。

## P0：给 `/api/history` 增加安全诊断日志

当前 access log 看不到 header，只能看到 401，无法从日志直接判断 history 是没有读 Bearer，还是读了 Bearer 但校验失败。

建议 history 接口在不输出 token 原文的前提下记录：

- `auth_mode=bearer|device_key|none`
- `uid=<Firebase uid>`，仅 Bearer 成功时记录
- `device_id=<device_id>`
- `range=24h|7d|30d`
- `ownership_result=ok|not_bound|db_error`
- `status=200|401|403|500`

不要记录完整 Firebase token。

## P1：设备上传鉴权的数据库连接需要自动恢复

日志里出现过设备鉴权数据库查询失败：

- `Lost connection to MySQL server during query`
- 随后 `/api/heartbeat`、`/api/upload` 出现连续 401

这类错误不应该被当成“设备 key 错误”。建议：

- `verify_device` 查询前检查连接是否可用。
- 使用连接池或每次请求获取新连接。
- 捕获 MySQL 连接断开后重连并重试一次。
- 如果重试仍失败，返回 503 或 500，并记录 `db_error`，不要返回 401。

### 为什么要改

401 表示客户端身份错误；数据库连接断开是服务器状态错误。混在一起会让 APP、固件、后台都误判问题来源。

## P1：生产环境不要使用 Flask development server

日志里反复出现 development server 警告。正式联调/上线建议切到：

- gunicorn + gevent/eventlet/thread workers，或
- uWSGI，或
- 其他生产 WSGI/ASGI 托管方式

### 为什么要改

开发服务器不适合生产长时间运行、并发请求、连接恢复和进程守护。当前项目包含设备心跳、上传、APP 轮询、后台页面，稳定性要求已经超过开发服务器范围。

## P1：后台 admin_key 不要放在 URL query 里

日志中后台接口把 `admin_key` 明文记录在 URL query。建议改为：

- `Authorization: Bearer <admin_token>`，或
- `X-Admin-Key: <key>`

同时 access log 对敏感字段做脱敏。

### 为什么要改

query 会进入浏览器历史、反向代理日志、应用日志、截图和错误上报，泄露面太大。

## P2：确认 daily_summary 的“有效数据日”口径

聚合日志显示有些日期只有 heartbeat 或几乎没有推理数据，仍可能写入 `daily_summary`。需要确认产品口径：

- 如果只有 heartbeat、无推理、监测分钟数为 0，是否算 7天/30天曲线里的有效数据日？
- 如果不算，需要聚合任务或 history 接口过滤这类 summary。

### 为什么要确认

否则 7天/30天曲线可能显示“有一天数据”，但实际没有有效焦虑/行为推理记录，用户会误以为设备当天完成了监测。

## 验收标准

Claude 修完后，用同一个 Firebase 登录账号验证：

1. 不带旧 key，只带 `Authorization: Bearer <Firebase ID token>`。
2. `GET /api/history/collar_001?range=24h` 返回 200。
3. `GET /api/history/collar_001?range=7d` 返回 200。
4. `GET /api/history/collar_001?range=30d` 返回 200。
5. 换一个未绑定该设备的 Firebase 用户，history 返回 403。
6. token 缺失或无效，history 返回 401。
7. 旧 key 路径如果保留，仍然返回 200，但 APP 不再依赖它。
